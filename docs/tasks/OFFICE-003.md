## Goal and acceptance criteria
1. A NEW opt-in test file test/scope-guard-oracle.test.mjs, run explicitly with `node --test test/scope-guard-oracle.test.mjs`. It is NOT added to guard group 1 or 2. Documenting it in docs/GUARD-SYSTEMS.md is a LATER step with its own scope and is not part of this task's scope.
2. Non-interference oracle: for every candidate command the hook ALLOWS (via the exported decide(), 2 roles x 2 tools), run it through the REAL shell in a throwaway repo, with synthetic secret files in state A, then state B. Verdicts (Owner decision O2):
   - FAIL: a file name, line count or content difference between the A and B outputs, or a canary string in the output.
   - WARN: same set of lines, different ORDER only.
   - FLAKY (A rerun does not match the first A run): counts as a harness error.
3. Candidate categories in phase 1: C1 benign controls; C3 drive-relative (`C:x`, `c:x`, `C:.env`, `C:../outside/..`); C5 backslash spellings (minimal subset, incl. `\--no-index`); C6 attached option values (`-O<p>`, `--relative=<p>`, `--exclude-from=<p>`, `--exclude-per-directory=<p>`); C8 PowerShell only (`@<var>` set by the harness to an outside synthetic file, comma pairs `a,b`).
   NOT covered in phase 1 (known limits): positional `..` and absolute paths (C2, C4: covered only by the existing unit tests), prefixes of dangerous long options (C7), colon and trailing-dot forms (C9).
   Drive letters: the drive letter used in candidates is DERIVED from the drive of the temp root (not hard-coded). A candidate that names a different drive (for example `Z:.env`) is not executed and is reported SKIPPED (its decide() result is still recorded statically); SKIPPED is never counted as PASS.
4. Execution restrictions (Owner decision O3): options that write or execute (`--output`, `--ext-diff`, `--textconv`, `-c`, `--exec-path`, `--open-files-in-pager`) are tested STATICALLY via decide() only and are never executed. Everything that is executed runs with cwd = the temp repo, a minimal environment built from scratch (no inherited GIT_* variables; no network; no remote), stdin ignored. The test never prints git output: only candidate, verdict, byte lengths and a hash.
5. Safety and cleanup (O6): one temp root from mkdtemp under os.tmpdir(); the test asserts its realpath is NOT inside the project root; synthetic data only; cleanup deletes only that mkdtemp directory. No other deletion.
6. Detector validity: (a) positive control: known-leaky argument lists run directly (not through the hook) must be flagged, else the test fails; (b) For each category: if at least one decide()-allowed candidate exists, at least one is executed. If none exists, the category is recorded STATIC_DENY_ONLY (never PASS) with its candidate count, and the category's mutant MUST turn at least one candidate into allowed and executed and the oracle MUST classify it FAIL. A category with neither is FAILED. (c) seeded bugs: mutant COPIES of the hook (and of scripts/guard-scope.mjs, copied next to it) are built inside the temp root, never in the repo: M1 removes the drive-relative check, M2 removes the backslash check, M3 removes the `@` check; the oracle must flag each. If a mutation target text is missing, the test fails loudly. The real hook file is untouched.
7. Hard limits (assertions, no silent sampling). Values below are PROVISIONAL (unmeasured proposal, safety ceiling for the first RED run only); the final limits are set from measurement:
   - max generated commands: 5000 PROVISIONAL
   - max executed commands per shell: 300 PROVISIONAL (exceeding it fails the test; narrow the grammar instead)
   - per-command timeout: 10 s PROVISIONAL
   - total runtime ceiling: 180 s PROVISIONAL (at that time; superseded by Owner decision 2026-11-14: default 240 s, calibration 720 s, oracle phase 90 s)

   The FIRST RED run must measure the per-command cost for each shell (Git Bash, powershell.exe) and for git, and record it here; the final limits change with that measurement.
   Cost check (arithmetic on an unmeasured assumption, NOT a measurement): the Owner's test output showed a node child process taking about 0.5 s; PowerShell and git cost were not measured. 2 shells x 300 executions x ~0.5 s is about 300 s, which would exceed the 180 s ceiling (at that time, before measurement; see Evidence, Criterion 7 measurements). Therefore the implementation must evaluate, and record the choice and its measured cost, between:
   - Option A, batching per shell: one shell process per state (A, B) per shell executes a whole batch of candidates, so shell start-up is paid once.    - Option B, a narrower grammar (fewer candidates per category, or fewer allowed-and-executed candidates).
   - A combination of both.
   The test prints a hash of the candidate list and a coverage summary (generated, allowed per role and tool, executed per shell, SKIPPED). A missing shell is SKIPPED, never PASS.
